I could not execute anything to confirm dynamically — my one Bash call (a scratch reproduction in `/tmp`) was denied by the permission mode. Everything below is static analysis of the five in-scope files, with the reachability path spelled out for each.

## CRITICAL

**1. `recover` accepts terminal evidence from a still-running runner — `scripts/execution-supervisor.py:191-193`**
The evidence read happens *before* the liveness check at `:194`, so ordering is inverted:
```
191  observed = terminal_from_evidence(...)      # read first
193  if observed: return finalize(..., observed) # finalize a live run
194  if pid_alive(int(state["pid"])):            # liveness checked only after
```
This is reachable on every run, not just after a crash: the plugin's recovery service walks *all* state files every `pollMs` (default 5000 — `index.js:273-281`) and only skips ones that are already terminal *and* delivered (`index.js:275`). So a `RUNNING` state gets `recover` invoked against it every 5s. Failure scenario: the managed runner writes a nonce-valid `RESULT.json`, then keeps working (writes `agent-result.json`, `MANAGED_OUTCOME.json`, flushes, exits ~seconds later). A tick landing in that window marks the run `SUCCEEDED`, appends the outbox event, sends the owner notification, and calls `runtime.finish` on the TaskFlow — while the agent is still executing. The stated invariant "terminal evidence is read only after runner exit" holds in `run()` (`:164-168`) but is broken in `recover()`. `test_forged_terminal_is_not_accepted_while_child_is_running` (`test_execution_supervisor.py:37-40`) only covers a *forged* nonce in the `run` path, so it does not catch this.

**2. Live supervisor clobbers concurrently-finalized state; exactly-once notification breaks — `scripts/execution-supervisor.py:165`**
The poll loop rewrites the whole in-memory state dict every `--poll` interval with no lock, outside the finalize `flock` (`:119-122`). Combined with #1: `recover` finalizes → state is `SUCCEEDED`, `notificationDelivered:false`; plugin sends and spawns `ack` (`index.js:240-246`); `ack` (`:200-204`) is itself an unlocked read-modify-write. Any interleaving with the live loop's write at `:165` restores `status:"RUNNING"` / `notificationDelivered:false`. Then the supervisor's own `finalize` at `:168` sees a non-terminal persisted status (`:124-125`), re-finalizes, and `notify_once` resets `notificationDelivered` to `False` (`:114`) — after the owner was already notified and acked. The next recovery tick re-sends. Concrete result: duplicate owner notification for a single run, and a state file that can transiently contradict the evidence file.

## HIGH

**3. `notify_once` is called outside the finalize lock — `scripts/execution-supervisor.py:190`**
The outbox dedupe is a scan-then-append (`:104-112`) that is only atomic because `finalize` holds the `flock`. The terminal-status branch of `recover` calls it directly with no lock. Two `recover` invocations racing (plugin restart overlapping the detached supervisor, manual CLI, or a second plugin instance — `activeRecoveries` at `index.js:229` only guards within one process) both scan, both miss, both append the same event id. `test_notification_exactly_once_after_recovery` (`test_execution_supervisor.py:52-55`) is strictly sequential and cannot catch this.

**4. Owner delivery is unreconcilable when delivery context is absent, and the configured fallback is dead — `projects/execution-supervisor-taskflow/index.js:237`**
`throw new Error("missing originating delivery context")` fires *before* any flow mutation (`:255-259`), so a run with empty `deliveryContext` never notifies the owner **and** leaves the TaskFlow stuck in `running` forever, re-throwing every 5s into `serviceCtx.logger.error`. The tool dispatch path passes `ctx.deliveryContext` (`:298`), which nothing in this plugin populates — unlike the ingress path, which builds it explicitly via `deliveryFromDispatch` (`:157-167, :199`). `JSON.stringify(deliveryContext ?? {})` at `:179` then persists `{}`, which passes the Python side silently and fails permanently on the JS side. The intended fallback — `config.delivery`, declared at `index.js:27-28` and `openclaw.plugin.json:23-33` — is **never read anywhere in the file**. The test only ever supplies `deliveryContext` (`index.test.mjs:64`), so this path is untested.

**5. A failed or never-dispatched admission permanently bricks the owner session — `projects/execution-supervisor-taskflow/index.js:220-226`**
`before_tool_call` blocks *every* tool whenever an `ADMITTED` record exists for the run/session. The only clearing path is `reconcileState` `:260-263`, which requires a terminal **state file** whose `statePath` matches. An admission that never dispatched has no state file, so `findStateFiles` (`:68-82`) never sees it and the map entry from `:152-153` never clears. Since `admissionsBySession` is keyed by `sessionKey` (`:106-109`), every later turn in that session is blocked too, with no escape hatch, and the persisted `admission.json` (status `ADMITTED`) is reloaded at `:120-125` after restart, so it survives a restart.

A concrete trigger is in the same file: `admission.sessionKey` is `ctx.sessionKey ?? null` (`:128`), and it is placed into the spawn argv unstringified at `:179`. A null session key makes `spawn` throw (`Arguments must be strings`) *after* the admission was persisted at `:151`, landing exactly in the wedged state. Any `createManaged`/spawn failure does the same, and additionally leaks a `running` flow created at `:170` that is never failed. With `"activation": {"onStartup": true}` (`openclaw.plugin.json:37-39`) this is an activation-safety hazard: a single dispatch failure disables all tool use for the owner.

**6. Managed admission is not idempotent without `ctx.runId` — `projects/execution-supervisor-taskflow/index.js:39-41`**
`admissionId` falls back to `randomUUID()`, so a context without `runId` gets a fresh id and a fresh `state/tasks/managed-admission/<uuid>` directory on every call, and the on-disk replay guard at `:120` (`persisted?.admissionId === id`) can never hit — it is looking inside a directory that by construction did not exist a moment ago. The only remaining guard is the in-memory one at `:116-118`, which for the no-runId case requires byte-identical `known.prompt === prompt`. Consequences: (a) after a plugin restart, re-sending the same objective dispatches a **second** managed run for the same work; (b) the same objective differing by whitespace/punctuation dispatches twice within one process; (c) the ingress path derives the prompt from `event.content` (`:200`) while `before_agent_run` derives it from `event.prompt ?? event.content` (`:112`), so the two entry points can disagree for the same request. The ingress path is precisely the one with no `runId` — `index.test.mjs:78-80` confirms it, reading the admission back out of a `readdir` because the id is unpredictable. The test asserts `length === 1` only after a single call, so re-admission is not covered.

**7. Terminal-capability confinement is advisory only — `scripts/execution-supervisor.py:155-159`**
The nonce is correctly kept out of the state file (only the SHA-256 at `:148`, verified by `test_execution_supervisor.py:36`), but the handoff gives the whole descendant tree the means to grab it: `pass_fds=(read_fd,)` (`:158`) clears `FD_CLOEXEC` on the read end, and `MANAGED_TERMINAL_FD` (`:156`) is exported into the child environment, which every process the model spawns inherits. The supervisor never closes the fd in the child and imposes no ordering requirement that the runner consume-and-close before the model gains execution — whichever descendant reads first wins the single-shot pipe. Separately, `PR_SET_DUMPABLE` at `:152` protects the *supervisor* only; `dumpable` is reset on `execve`, so the runner process that actually holds the nonce in memory is same-uid inspectable by anything the model runs. Whether this is exploitable end-to-end depends on `scripts/managed-agent-runner.mjs`, which is outside the inspection scope you set — flagging the supervisor-side gap, which is real regardless of what the runner does.

## What passed

- **Exit code 0 alone is never `SUCCEEDED`** — `execution-supervisor.py:169` maps `code == 0` to `FAILED`; `SUCCEEDED` requires `terminal_from_evidence` with `contractValidated is true` *and* a nonce whose hash matches (`:65-66`). Fail-closed when the file is absent, unparseable, or the status is unmapped. Stale evidence is unlinked pre-launch (`:135`). `--require-validated-terminal` (`:214`) is parsed but never read — validation is implied by `--terminal-evidence` presence (`:146`), which errs in the safe direction.
- **Terminal evidence after exit** — correct in `run()` (`:164-168`); broken only in `recover()` (finding #1).
- **No arbitrary-command start surface** — the only registered tools are `execution_supervisor_dispatch` (zero-parameter, `index.js:291`) and `execution_supervisor_recover` (single `statePath`); the argv at `index.js:176-183` is fully plugin-constructed. `openclaw.plugin.json:7-10` matches. `index.test.mjs:65` asserts the old `execution_supervisor_start` is gone.
- **High thinking** — `config.managedAgentThinkingLevel ?? "high"` (`index.js:183`), schema default `"high"` (`index.js:22-24`, `openclaw.plugin.json:20`), enforced by the fake runner at `index.test.mjs:22`.
- **RU/EN large-objective matching** — `requiresManagedExecution` (`index.js:32-37`) covers explicit completion-notification phrasing in both languages plus the ≥600-char objective heuristic, and correctly returns false for short conversational prompts. Nested managed sessions are excluded (`index.js:114`). Coverage gap, not a defect: only imperative-familiar Russian forms match — "Выполните…", "реализуйте…" fall through to the length heuristic.

Minor, non-blocking: the `blockReason` ternary at `index.js:223` is dead (the `:222` guard already returned for `DISPATCHED`); `safePath` (`:57-62`) canonicalizes the root but not the target, so an in-workspace symlink escapes the prefix check, and `recover` then writes to the unvalidated `evidencePath`/`outboxPath` read out of the state file (`execution-supervisor.py:188`) — owner-gated, so low severity; `admissionsByRun`/`admissionsBySession` grow unbounded for runs that never reach terminal.

**FAIL** — findings #1 and #2 break the core execution-truth invariant (a still-running agent can be reported terminal, notified, and its flow finished), #4 and #5 are activation-safety defects that can permanently wedge either the flow or the owner's session, and #6 permits duplicate dispatch of the same objective.
