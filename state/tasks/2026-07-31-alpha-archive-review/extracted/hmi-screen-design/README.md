# Как развернуть этот навык

Пакет платформо- и модель-независимый. Ниже — что грузить в зависимости от того, какой у вас агент. Выберите один сценарий.

## Что в пакете

| Файл | Символов | ~токенов | Назначение |
|---|---|---|---|
| `CORE.md` | 13 700 | ~5 700 | Ядро: принципы, порядок работы, ключевые числа, маршрутизация по справочникам |
| `COMPACT.md` | 7 900 | ~3 300 | Сжатое ядро под поля с лимитом 8 000 символов |
| `ALL-IN-ONE.md` | 83 700 | ~34 800 | Всё содержимое одним файлом |
| `references/*.md` | 63 800 | ~26 600 | Семь тематических справочников |
| `rules/hmi-rules.json` | — | ~11 000 | 84 атомарных правила с обоснованием, способом проверки и пометкой происхождения |
| `assets/hphmi-palette.json` | 5 000 | ~2 100 | Палитра, кегли, отступы, зоны нажатия машиночитаемо |

Оценка токенов для o200k (GPT-4o и новее, Claude, Gemini). Для cl100k (GPT-4, GPT-3.5) умножайте примерно на 1,7 — кириллица там режется значительно хуже.

## Сценарий 1. Агент умеет читать файлы

Подходит для: Claude Code, Cowork, Cursor, собственный оркестратор с файловым доступом, любой агент с инструментом вида `read_file`.

Скопируйте папку целиком. В системный промпт положите **`CORE.md`**. Дальше агент сам открывает нужный справочник по таблице в конце ядра.

Постоянные расходы — около 5 700 токенов, типичный запрос добавляет один справочник, то есть 3–7 тысяч. Это самый экономный и самый точный режим: агент берёт нужный файл целиком, без выдачи семантического поиска.

## Сценарий 2. Агент со skills (экосистема Anthropic)

Переименуйте `CORE.md` в `SKILL.md` — фронтматтер уже на месте. Упакуйте папку в `.skill` или положите в каталог навыков. Дальше механика трёхуровневая: постоянно в контексте висит только описание (~400 токенов), тело подгружается при срабатывании, справочники — по мере надобности.

## Сценарий 3. Поле инструкций с ограничением

Подходит для: Custom GPT в ChatGPT (лимит 8 000 символов), GPT Store, короткие системные промпты, узкие контекстные окна.

В поле инструкций — **`COMPACT.md`** (7 891 символ, запас 109). Справочники и `rules/hmi-rules.json` загрузите в раздел знаний.

Важно: `COMPACT.md` самодостаточен и работает даже без справочников — там есть все ключевые числа. Справочники добавляют детализацию, но не являются обязательными.

## Сценарий 4. RAG или векторное хранилище

Подходит для: Assistants/Responses API с file_search, LangChain, LlamaIndex, собственный RAG.

Системный промпт — **`CORE.md`** или `COMPACT.md`. В индекс — справочники и `rules/hmi-rules.json`.

Про нарезку: справочники разбивайте **по заголовкам второго уровня**, не по числу символов вслепую. Правила там атомарные, и раздел про выравнивание чисел осмыслен сам по себе. `hmi-rules.json` индексируйте **по одному правилу на чанк** — структура для этого и сделана, каждое правило самодостаточно и содержит поле `check`.

## Сценарий 5. Ни файлов, ни поиска

Подходит для: агент с одним большим системным промптом, оффлайн-модель, встраивание в чужой продукт.

Грузите **`ALL-IN-ONE.md`** целиком — около 34800 токенов. Помещается в контекст любой современной модели, но занимает его постоянно.

Если контекста мало, минимальный работающий набор: `COMPACT.md` + `references/layout-and-typography.md` + `references/color-and-symbols.md`, суммарно около 11 тысяч токенов. Хватает на компоновку и палитру, то есть на большинство практических вопросов. Тревоги и элементы управления добавляйте, когда задача до них дойдёт.

## Сценарий 6. Программная проверка без модели

`rules/hmi-rules.json` пригоден для линтера, который проверяет проект SCADA без участия ИИ вообще: выгружаете описание экранов, сопоставляете с правилами по полям `category` и `severity`, получаете отчёт. Поле `check` описывает способ проверки, `values` содержит эталонные значения.

```python
import json
rules = json.load(open('rules/hmi-rules.json'))['rules']
critical = [r for r in rules if r['severity'] == 'critical']
colors = [r for r in rules if r['category'] == 'color']
```

## Если агент игнорирует навык

Самая частая проблема при переносе на модели без механизма skills: агент отвечает про экраны своими словами, не заглядывая в правила. Лечится так:

1. **Усильте формулировку срабатывания.** В начале инструкций должно стоять императивное «прежде чем отвечать про экраны, цвета, надписи или сигнализацию — сверься с правилами», а не «можешь обратиться к справочнику». Слабые модели игнорируют разрешительные формулировки.
2. **Добавьте свою лексику.** Впишите слова, которыми пользователи реально пишут у вас: названия вашей SCADA, «мнемосхема», «переделать экран», «почему плохо читается».
3. **Проверьте, что маршрутизация выполнима.** Если в инструкциях написано «прочитай `references/alarms.md`», а инструмента чтения файлов у агента нет — он просто проигнорирует указание. Уберите или замените на формулировку под ваш механизм.

## Проверка, что всё работает

Три запроса, по одному на каждый тип задачи:

1. *«Сделай экран для узла: насос, теплообменник, ёмкость»* — должен спросить про оператора и задачи либо явно обозначить допущения; предложить серую палитру, шкалы с границами, поток слева направо.
2. *«Вот скриншот нашего экрана, что не так?»* — должен разбирать конкретную картинку и выдавать находки с приоритетами, а не пересказывать принципы.
3. *«Каким цветом показать работающий насос?»* — должен ответить `#F0F0F0` (почти белый) и объяснить, почему не зелёным.
4. *«Можно ли показать только часть однолинейной схемы?»* — должен различить параметрические и топологические решения и сказать, что для переключений контур замыкается до источников.

Если на третьем вопросе агент отвечает «зелёным» — навык не подключился.

## Адаптация под себя

Пакет — заготовка, а не догма. Что имеет смысл дописать:

- **Свой стандарт предприятия** — как приоритетный источник, выше референсных чисел Rockwell.
- **Отраслевую специфику** — требования к экранам в вашей отрасли (АЭС, фарма с валидацией, нефтегаз) отличаются.
- **Маппинг на вашу платформу** — отдельный справочник вида «правило → как это делается в WinCC/Ignition/у нас».
- **Свои антипаттерны** — то, что регулярно приходится исправлять именно у вас.

## Источники

ANSI/ISA-101.01-2015; The High Performance HMI Handbook (Hollifield, Oliver, Nimmo, Habibi, PAS, 2008); Rockwell Automation Process HMI Style Guide (PROCES-WP023A-EN-P, 2019); ANSI/ISA-18.2-2016; ANSI/ISA-5.1; ISA-5.5; EEMUA 191/201; ISO 11064; ISO 9241-210.

Числовые значения (RGB, пиксели, кегли) взяты из библиотеки Rockwell PlantPAx как проверенной референсной реализации принципов ISA-101 и HPHMI. Это не прямые требования самого стандарта ISA-101 — он методологичен и конкретных цветов не предписывает.

Часть правил раздела о законченности схем (замкнутость по типу решения, накопленная энергия, специфика однолинейных и гидравлических схем) — реконструкция из инженерной практики, а не цитата из стандартов. В `rules/hmi-rules.json` такие правила помечены полем `basis: practice`; в проектной документации оформляйте их как внутреннее правило предприятия и не ссылайтесь на ISA-101.
